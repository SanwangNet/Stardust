# Starcore Channel 入站执行 M3-C2

## 真实路径

QQ SDK 的 `message` 回调进入 QQ 星核 `receive`。QQ 星核识别 C2C 与群事件：C2C 只接受 `C2C_MESSAGE_CREATE`；群聊接受官方 `GROUP_AT_MESSAGE_CREATE`，或在普通群消息中检查 `mentions.is_you` / AppID 的 @ 标记，并验证群与回复目标。原有过滤还检查机器人发送者、消息与目标、内容、去重、回声、限流及队列容量。通过后，QQ 记录诊断目标并排队，将裁剪后的内容、消息和会话标识封装为 `ChannelMessage` 调用 Core `host.message`。正常应用将其路由至单一主 Agent 的 `chatChannel`，使用既有主 Agent 提示词和当前消息请求模型；备用配置沿用 `model.chat`。QQ 再使用原目标发送模型结果。QQ 没有因此获得 Web Conversation、Web Global Context 或 History Retrieval。

`STARDUST_QQ_INPUT_FLOW=1` 在 QQ 星核启动时启用新路径，默认关闭，环境变量更改后需重启星核。启用时 QQ 回调将请求交给该运行实例的 Core 宿主，由 Core 快照并校验声明、契约指纹、节点组和固定适配器，然后执行嵌套节点组。`qq-bot:diagnostic` 执行原有脱敏接收日志，是可断开的可选分支；`qq-bot:accept` 调用相同的 QQ 过滤函数，属于必需节点。两条路径共享该函数及运行时状态。主 Agent、模型、Tool、审批和 QQ 发送都不在这张图内。

图中只传递本次生成的不透明令牌，不序列化 SDK 事件。输入、输出及子组接口类型和副标题来自服务端声明。过滤节点返回 Core 随机生成的另一个本次凭证；只有该节点恰好执行一次且输出匹配，才允许读取 `allow` / `skip`。因此断开过滤或将输入直接连至输出均不能放行。可选诊断断开时其日志回调不执行；过滤失败为 `skip`，不会进入模型。校验或执行错误记录脱敏错误并停止，不回退旧路径。

## 信任与生命周期

只有 Core 硬编码的 `core:qq-input` 与两个固定节点 ID、精确角色和端口匹配；清单无法提供代码。请求上下文由 Core 构造，含固定 Channel/Starcore ID、事件和 QQ 本次消息/会话标识、截止时间、仅 `qq:inbound` 能力及合并取消信号；没有 Web 数据源、Tool 或审批能力。QQ 原始数据只由本次 QQ 回调闭包访问。该边界依赖受信的内置星核与进程内代码：现有扩展系统并非第三方沙箱，不能隔离已在服务进程中运行的恶意 JavaScript。

每个请求克隆组定义、重新验证声明与安装时指纹，并创建固定的注册表和回调绑定；宿主在每次请求检查运行实例、连接及安装/启用状态。停用或卸载会中止该实例的生命周期信号，旧宿主不能用于新请求。5 秒截止时间与请求和生命周期信号共同传给适配器，取消后不再启动下一阶段。当前两个 QQ 回调同步，取消不能抢占正在运行的同步代码；未来异步回调必须自行遵守信号，无法强制撤销已经开始的外部操作或副作用。过滤已经更新的去重/限流状态也不会因后续取消而回滚。

M3-C1 的已知 QQ 内置声明指纹可迁移到本版固定声明：公开根组的接口 ID 和类型不变，新增可选内部诊断输入。只认可该特定旧指纹到本版精确契约的迁移，其他不兼容变更仍拒绝启用或恢复，且不替换为其他类型。

目录分别报告注册/启用状态、运行状态、`executable`、`flowSwitch` 和 `requestChain`。界面只读；它不发布 QQ 节点连接，也不更改 M4-A 的三条 Web 发布连接。Web 的现有执行路径、工具与审批保持独立。

## 验证与后续

`tests/qq-input-flow.test.mjs` 使用模拟 QQ 事件、模拟网关与模型，覆盖图执行、断线与重连、防绕过、契约伪造、取消和超时、旧/新路径等价、生命周期及队列容量。未连接真实 QQ 或真实模型。Web Context、Tool、审批与发布仍由原有回归测试覆盖。

后续应先定义 QQ 会话和用户作用域及明确授权，再把 QQ Context 接入统一 Conversation；统一 Agent 输入应保持一个主 Agent 并明确跨渠道记忆授权。Skill Runtime 是独立阶段，需单独设计注册、权限和执行隔离，本阶段没有实现。
